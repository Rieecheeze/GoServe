# GoServe v2.3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development to implement this plan task-by-task. Preserve completed work and its verification evidence.

**Goal:** Replace the native foundation's placeholder workflows with the approved v2.3 Android application and matching Supabase contracts.

**Architecture:** Keep Java/XML, existing ViewBinding, AndroidX fragments, ViewModel/LiveData, fonts, assets and configured Supabase client. Add server-authoritative operations behind table-specific RLS, shared session-scoped realtime invalidation, and native feature repositories. External provider operations remain unavailable until their documented contracts and readiness settings exist.

**Tech Stack:** Java 17; Android API 26–35; Gradle 8.9; PostgreSQL/Supabase Auth, Storage, Realtime and Edge Functions.

**Spec:** `docs/GoServe-project-plan-v2.3.md`, matching `output/pdf/GoServe_Project_Plan_v2.3.pdf`. The user approved the finished UI and explicitly authorized code execution on 17 October 2026.

## Global Constraints

- Native Java/XML only. Preserve existing keys, local SDK settings and provider configuration.
- Use the original GoServe Android v2.1 Figma page for visual fidelity and the approved v2.3 overview for workflow changes. Preserve Montserrat/Karla typography, monochrome surfaces, capsule navigation and supplied assets.
- Student, Staff and Teller are the only roles. Faculty, Guidance and CCS secretary are Staff capabilities provisioned by trusted administration.
- Version 2.3 supersedes older documents. No Firebase, autonomous AI mutations, invented service fees, invented legal text, fictional operational records or persistent Seryo chat history.
- All writes enforce authorization in PostgreSQL or a trusted Edge Function. Public registration can create only a Student. Never expose service-role keys to Android.
- Missing policy/provider configuration blocks the affected action with a useful explanation. It does not produce fake success or a simulated payment/AI response.
- Requests use exactly Submitted, Awaiting Payment, Processing, Ready for Pickup/Download, Completed, Cancelled and Rejected. Payment states are separate.
- Free requests create no payment. Pending fee declarations block submission. Required fees are revalidated and frozen atomically with submission.
- Duplicate submissions, messages, cash confirmations, handovers and receipts are idempotent. Capacity and rescheduling are transactional.
- Ready alone never issues a pickup code. Student Claim issues/reuses one active private code. Authorized explicit handover consumes it once.
- Digital completion requires a successfully recorded download of the released version, followed by explicit student receipt confirmation.
- Account change/sign-out cancels subscriptions and in-flight work and clears local account data. Reconnect reloads canonical data.
- Seryo has separate Allow/Decline consent; one PDF/JPG/PNG at most 10 MB; explicit Send; unsent Explain/Extract drafts; verified temporary cleanup.
- Do not deploy database/Edge changes or enable providers during local implementation. Prepare reviewable deployment artifacts and test evidence first.

## Review Focus

1. Late responses and realtime events from an old account must never appear under the next account.
2. Concurrent retries must preserve one financial/request/booking result and immutable fee snapshots.
3. A caller must not cross student, office, capability or Teller boundaries through direct REST/RPC calls.
4. Missing policies/providers, interrupted downloads and temporary-file cleanup failures must leave durable state truthful and retryable.
5. Phone widths, large text, back navigation, process restoration and reduced animation settings must preserve accessible controls and drafts.
