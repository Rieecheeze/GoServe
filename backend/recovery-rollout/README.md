## Password Mutation and Uncertain Results

The service atomically consumes a code to issue a five-minute grant bound to its owner, purpose, security version and S256 installation verifier. Claiming the grant records one job and advances the account security version before calling Auth. A unique pending-job index blocks a second reset or code generation for that owner. Duplicate operation IDs reconcile instead of sending another password mutation. Another operation cannot reuse the grant.

The hosted Auth health endpoint reported GoTrue `v2.197.0` during read-only preflight. In that exact primary-source tag, [Admin update](https://github.com/supabase/auth/blob/v2.197.0/internal/api/admin.go) executes `UpdatePassword(tx,nil)` and `UpdateAppMetaData(tx,params.AppMetaData)` within the same database transaction. [User model](https://github.com/supabase/auth/blob/v2.197.0/internal/models/user.go) merges supplied app-metadata keys and logs out sessions for that password update. The request supplies only `goserve_recovery_op`, preserving existing role/provider metadata. This is deployed-version/source evidence; it is not a live password mutation test.

Before release, an isolated fixture must confirm that a Google-only user can set its first password, existing metadata survives, all previous sessions are removed, and normal sign-in issues the new session. Also exercise an accepted mutation with a lost response and a definitive rejected mutation. The Edge response never issues tokens or authorizes Home. Android signs in normally only after authoritative `completed`.

A matching server-owned operation marker proves an uncertain Auth update committed. Missing markers or failed provider reads remain `pending`; the service never guesses failure and never replays a password. Result polling works for 24 hours after claim. An unresolved job intentionally blocks further mutation and needs trusted provider/database reconciliation. Do not mark it failed merely because time passed; first establish that the original provider operation cannot still commit. Do not copy passwords, raw codes or grants into support/audit records.

## Native Auth Boundary

Recovery codes are the GoServe app's Forgot Password and Change Password flow. They do not replace Supabase Auth's own authenticated API policy. In GoTrue v2.197.0, an otherwise valid current session can call the native user-update API under the provider's password/reauthentication rules. That is authenticated account access, not this public recovery endpoint, and it must not be described as requiring a GoServe recovery code. The per-owner pending-job lock serializes GoServe recovery mutations; it cannot serialize every independently authorized native Auth or administrative password update. Android still performs normal password sign-in after a completed reset and reports a failure honestly if another authorized update changed that password.

## Storage and Rollback

Each generation returns ten independent CSPRNG 160-bit Base32 codes once. Only domain-separated SHA-256 code digests enter private RLS tables. All historical digests remain globally reserved; regeneration revokes the old unused set atomically. Grants, operations and audit rows contain no plaintext codes or passwords. Account and trusted-IP budgets are durable fixed fifteen-minute windows; verification consumes both even for unknown accounts. Status cannot retrieve old plaintext. A lost generation response requires fresh protected regeneration.

Prefer disabling public recovery at the gateway for rollback while leaving strict session enforcement enabled. Disable `enforce_readiness` only if rolling Android back is necessary; preserve all code/grant/job/audit records. Do not drop tables, revive an old generation, restore retired email endpoints, disable the TIP registration hook or disable session checks while public reset remains reachable. Claimed result reconciliation must remain available for uncertain operations. Recovery data has no automatic deletion policy in this release; approve retention separately before any cleanup is introduced.

## Local Evidence and Limits

Run `npm test --prefix backend`, and Deno-check the two new and three retired function entrypoints. The focused tests cover exact DTOs, bounds, fresh authentication, stale/revoked sessions, code uniqueness/owner binding, one-time consumption, grants/versions, queued duplicate claims, pending-result reconciliation, Terms/profile order, last-code readiness, canonical Auth email and fail-closed registration/email routes.

PGlite `Promise.all` requests are serialized by one database instance. They prove state transitions, constraints and idempotence, not separate-connection lock contention. Native PostgreSQL executables could not start on this Windows host (`0xC0E90002`); no security setting was weakened and no replacement binary was downloaded. Independent-session PostgreSQL claim/regeneration races, actual hosted ingress trust, provider mutation/session effects and device integration remain explicit live/isolated verification gates.
